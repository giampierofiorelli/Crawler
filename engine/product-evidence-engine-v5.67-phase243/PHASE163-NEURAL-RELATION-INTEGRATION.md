# Product Evidence Engine v4.87 — Phase 163: GLiNER2.5 relation proposals in the PEE batch path

**Baseline:** v4.86, Phase 162. **Status:** implemented and tested at the **API-contract and orchestration** level, NOT evaluated with the pretrained GLiNER2.5 relation decoder. Date: 12 October 2026.

## Why this change

The previous GLiNER2.5 pilot used its entity-detection function to identify product names, brands, features and numerical values. That is insufficient to know **which product has which characteristic or measurement**, particularly when competing models occur in one article. The original GLiNER2.5 code and model card also expose `extract_relations` and `JointIE`. The model card specifies that the checkpoint was trained with relations enabled, **but independent decoding does not guarantee correctly typed endpoints**. Consequently, PEE now supports optional relation proposals and checks their source attachment and endpoint types before exposing the proposals to the remainder of the batch. It does **not** treat high neural confidence as scientific proof.

## What was integrated

1. `scripts/phase163_neural_relations.py` calls the original local `AutoExtractor.extract_relations()` API on bounded overlapping windows, with **three relation hypotheses**: `product_has_feature`, `feature_has_measurement`, `product_compared_with`. It checks both endpoints against the original window, converts code-point positions to PEE's UTF-16 offsets, deduplicates overlap candidates, enforces 150 document-level relation budget and fails rather than silently dropping corrupted spans.
2. `scripts/phase161_neural_worker.py` now has an **opt-in `--with-relations` mode**. When enabled, the same loaded model runs the entity and relation passes without downloading additional checkpoints. Persistent cache keys include the optional mode and implementation digest. Cached relation spans must pass the original source-offset and authority-flag checks; tampering causes re-execution/quarantine, not implicit acceptance. Default operation is unchanged.
3. `src/phase163_relation_candidate_bridge.ts` validates each proposed relation against raw text and source-bound neural entities, classifies endpoints as `matched` or `mismatch_or_missing`, and retains contextual category flags. It never infers product identity solely from a shared brand, nor does it turn a model relationship into an approved reviewer test result. It explicitly sets `identityVerified`, `scientificEvidence`, `publisherTestStatusVerified`, `canonicalWriteAuthorized`, `rankingAuthorized` to `false`.
4. `src/phase160_batch_review_pipeline.ts` invokes this bridge within its existing authenticated-local-worker-audit path, producing relation hypotheses alongside entity/context/measurement signals. Malformed proposals quarantine the affected document. Previous two genuine external **entity-only** Colab examples remain backward compatible. Results made to look like Colab cannot smuggle in unaudited relation proposals.
5. `scripts/phase163_relation_eval.py` adds separate exact source-span typed-relation evaluation. It can score all proposals and label-compatible proposals against independently supplied gold annotations; the software does **not** claim that annotations are independent, blind or publisher-authorised. No reviewer/producer boundary, comparability or canonical evidence is validated by this scorer.

### Example of what the new path could propose

For the **developer-constructed Maytag** snippet previously used to test entity extraction, the application tests created hypothetical relations linking `MRT311FFFE` to `cooling noise`, `cooling noise` to `44.9 dBA`, and `MRT311FFFE` to the compared `GTS22KGNRWW`. Those **relation hypotheses were generated by the test fixture**, **not by executing GLiNER2.5**. The bridge correctly checked their UTF-16 endpoints and matched them against the real, previously recorded entity predictions. Corrupted strings, offsets, self-links, fabricated types, duplicated relations and approval flags were rejected.

The model's actual neural relation output might be different or might fail to find some relationships. There is no claim of relation recall, precision, superiority or generalized review comprehension.

## Checks and concrete results

- TypeScript build passed using the same locally available development type packages as before; **2,092 TypeScript tests across 122 eligible files**, divided into 11 complete groups. The longstanding Phase91/92 legacy suites are excluded, as in previous releases. All 11 groups succeeded, 0 reported failures.
- **103 Python tests passed**: 47 primary-source, 21 ingestion and 35 optional-model/benchmark tests, including **8 new Phase163** tests.
- The new worker-specific test demonstrates cache reuse only when relations are enabled with a matching cache key, and verifies mode separation. It uses a deterministic *fake extractor*, **not pretrained model inference**.
- Integration tests also checked the legacy external-Colab path, source tampering, role preservation, relation type mismatch and unauthorized authority flags.
- Historical PEE artefacts and notice files retained; no external ZIPs or pretrained checkpoint in this release. Manifest records changed files and sizes; original full review contents are not packaged.

## Current blocking conditions

- **No persistent inference host with the real GLiNER2.5 checkpoint is available to this development workflow.** This release does not contain real relation predictions or neural runtime benchmarks. The only genuine neural output still originates from the prior two developer-constructed **entity** examples executed on Colab.
- **No publisher-rights-cleared corpus of complete professional English reviews**, across publishers and product families, with separately adjudicated blind gold annotations, has been supplied or authenticated. Existing short RTINGS passages are development diagnostics only.
- New relations are optional. A model can suggest the wrong direction or confuse a manufacturer's specification with an independently observed laboratory measurement; the native evidence, source-role, identity and ranking controls remain mandatory. `JointIE` is a candidate for later empirical comparison, **not an integrated or evaluated component**.

## Reproducing on a future trusted model host

With a reviewed checkpoint already installed and operator lock provided (see Phase161 technical report), pass `--with-relations` to the existing resident worker invocation. Then the same `scripts/phase161-coordinate.mjs` passes the worker's source-bound relation proposals into PEE. No extra user-side model upload or public website change is required. `scripts/phase163_relation_eval.py` accepts `--manifest`, `--coordination`, `--gold`, `--out` for private typed-relation evaluation.

The release deliberately leaves these choices unexecuted until a trusted host and legitimate source corpus are available. Neither the shipped test data nor any third-party editorial article is represented as independent neural evaluation.
